# Magnet 出题：给 agent 的工作说明

`magnet/` 唯一的总说明。规则以出题规范 v4.5（2026-11-16）为准，旧经验与它冲突时按 v4.5。每道题要填的原文在该题目录的 `README.md`。

用户的固定要求：

- 全程用中文回复。
- 题目从 `high-econ/` 和 `finance/` 的现成题一对一转换，不合并。不再为 Magnet 现编小题。
- 文件产出最小化。每道题一个目录，只留 `README.md`、`附件/`、附件包和打包脚本。
- 已领的题有进展直接处理，不用逐步请示（2026-11-17）。git 提交和推送仍然等用户开口。
- 工作台链接里的 token、签名下载地址不写进仓库。
- 交附件之前先过下面两道闸。只过第一闸的题不交。

## 先过两道闸，再交附件

附件一旦过了附件机审就锁定，之后只能改 Query，再往后只能改评估表。两道闸都要在交附件之前过。

### 第一闸：难度筛查

题目机审通过后，平台让模型试做一遍，综合看材料构成、处理投入、执行过程和产出规模。过于简单的退回「附件待提交」，意见只有一句「题目过于简单，请重新出题」。此前掌握的口径是模型执行不到 25 步就退回。

过这一闸靠的是：

- 至少三件互相独立、各自要读材料出结果的工作。几份交付物如果是同一段程序的输出，只算一件。
- 材料是业务里拿到手的原始形态，整理和核对本身就是工作。不替模型合并、筛选、对齐。
- 有第二套数字可以对账：另一位同事的结果、另一个数据来源、新旧版本的规则。
- 规则文件写业务规则，不写成照着就能编程的步骤表；不用一份交办把每个附件的用途列成清单。
- 自己掂量：一个熟练的人能不能写一段程序把全部交付物一次跑出来。能，就不交。

### 第二闸：评估表的分布

评估表 B 模块只统计「关键」和「重要」的条目，要求：至少 7 条有两家及以上不满足，其中至少 3 条三家都不满足，另有至少 1 条恰好一家不满足；每家至少 3 条真实缺点，B 合计至少 8 条。缺点必须是产物里真实存在、能定位的，不能编、不能拆、不能夸大。格式和显示类问题会被机审降成「一般」，不计入。

所以三家把关键数字全做对的题，评估表交不出去，题目只能废弃。评估阶段改不了附件。

过这一闸靠的是：

- 材料里有至少 8 处要读细才处理得对的边界，每一处都能改变金额、时点、名单或结论。
- 每一处边界在原始数据里真的被踩到。写进规则却一次都没发生的边界不算。交附件前用标答程序逐条验证，把「去掉这条规则，结果变不变」跑出来。
- 标答在每一处都确定，能用附件复核。
- 计算有路径依赖（持仓、止损、权益逐日带着走）的题，三家更容易算出不同的数。每笔独立、算式固定的题，三家通常全对。
- 交付物里有要写判断和解释的部分：差异原因、口径核对结论、结论为什么仍然成立。
- 最终结论不要在任何算法下都一样。结论对边界不敏感时，关键条目很难成立。

三家实际踩过的边界类型（新闻过滤，2026-11-13）：

1. 等于也算触及。价格刚好等于止盈价的那一根，三家都晚了一到两分钟。
2. 和常规安排不同的日期（提前、改期、落在非惯例星期几），两家漏标。
3. 同一事实在两份交付物里对不上，一家的建议书和自己的台账矛盾。
4. 两个相近的计数（工作日数和有报价的交易日数）被写混。
5. 推荐方案本身是亏的，一家没有写出来。

这些加起来仍然不够 7 条，那道题最后废弃。要的是比这更多的真实分歧点。

### 交附件前的核对单

1. 列出互相独立的工作，至少三件。
2. 列出边界清单：每条写明在哪份材料、数据里哪一天哪一行踩到、踩错后哪个数字变成多少。不足 8 条不交。
3. A 模块要写得出至少 15 条互不重复的标准：结果正确性、专业质量各至少 4 条，指令遵循、格式各至少 2 条，语气与沟通至少 1 条，单类不超过 40%。写不出 15 条说明题太薄。
4. 附件是真实业务材料，没有编号式的假数据，没有验收提示、解题步骤和例题。
5. 预计耗时能用材料规模和步骤解释，按环节拆得出来。
6. 和已交的题去掉名称和数字后不是同一副骨架（附件职责、判断节点、交付结构）。

## v4.5 里会直接退回或拒绝的

任务说明和附件：

- 预计耗时不少于 480 分钟，低于即拒绝。明显虚高、材料规模解释不了的也不过。填整数。
- 业务背景不少于 60 字，任务目的不少于 30 字，具体任务要求 1 到 5 条、每条 20 到 50 字、只写结果不写操作顺序。
- 核心附件至少 5 个，至少两类格式（xlsx、xls、csv 算一类），至少一个私有。不机械拆分凑数。删掉附件后只靠 Query 做不出大部分产物。
- 禁止 AI 构造的假业务文件。附件里不能有答案、解题步骤、最终名单、评分点、验收提示，不能出现「本题」「出题」「考点」这类话。
- 压缩包平铺，不套文件夹。单文件建议不超过 20MB。噪音不超过 30%，不得恶意误导。
- 交付物写全文件名和扩展名，和以后的 Solution 一致。
- 难度不能来自缺信息、矛盾、模糊表达、噪音、超长文字或无意义步骤。

Query：

- 系统只给 1 份初稿，可以改，也可以自己写。附件已锁定，缺材料不能在 Query 里编。
- 不泄答案：不点名实际的异常、对象、名单、数值、正负结论。
- 不固定路径：不规定先看哪条、按什么顺序、超过多少就判成什么。
- 不加任务说明里没有的对象、期间、指标、交付物。
- 异常处理写成条件式：保留已确认事实，标待核，说明对结论的影响。
- 不出现出题和评测用语，没有语病和乱码。
- 本账号用四段模板：【背景】【范围】【要求】【输出数量、名称、格式、具体要求】。

评估表：

- A 至少 15 条，配额见核对单第 3 条。每条写依据、验收对象、合格条件、边界，不提模型。两条 A 不查同一个判断。
- B 的三家情况只选「满足」或「不满足」。只有关联的 A 是多档时才用「部分满足」。
- B 每条要有：通用的评估项描述、三家证据（文件名加位置）、合格时应满足的具体状态、例外边界、依据位置。
- 影响程度按业务后果定。只影响显示和版式的记「一般」。
- 新题没有「业内共识」勾选。对机审意见有异议，在评估页右侧「专家反馈」里勾「提出异议」并写理由。
- 机审结果是「通过」或「需审核确认」时不用改；「不通过」时只改标「需处理」的条目。

Solution：

- 按当前 Query 和附件做完全部交付物，不是评估表，也不是对三家的点评。
- 机审按评估表里 A、B 条目的满足率判，达到 80% 通过。不通过只改 Solution，不能回头改标准。
- 成品里不出现模型编号、评分、机审意见、「标准答案」。

返修和拒绝：

- 人审最多打回 3 次，第 4 轮不过即拒绝。附件一眼假直接拒绝。
- 人审因 Query 或题包问题打回后，M1、M2、M3 会重新生成，评估表要按新产物重填，Solution 也要对齐。
- 申诉入口在工作台右上角，按「争议点、原意见、证据、应如何判定」举证。

## 题目目录

```
magnet/
  AGENTS.md
  代填脚本.py
  NN_领域_题名/
    README.md        页面上要填的全部字段，按页面顺序
    附件/             压缩包里的原件
    题名_附件包.zip    不入库
    打包.py           打包并核对，不上传
```

`README.md` 的格式是 `代填脚本.py` 的输入，不要随意改：

- 字段用三级标题，标题就是页面上的字段名，内容放在代码块里，代码块外不写解释。
- 附件清单是三列表格：文件、公开/私有、核心/噪音。
- 交付物标题写成「交付物 N｜文档｜.docx」，下面两个代码块，先文件名（不带扩展名），后内容要求。
- Query 页有「参考 Query」和「Query」两个字段。

## 代填工作流

浏览器用 `browser-use` 这个 MCP，主要是 `evaluate_script`，传一个函数声明，单次上限 15 秒。不要派浏览器子代理。

### 找到工作台

题目列表：`https://fellow.meetchances.com/project-quiz?project_id=160&project_name=Magnet项目&tab=mine`。

领新题：点「领取题目」页签，找到方向卡片里的「领取 1 道」，弹窗里核对方向后点「确认认领」，页面提示「题目领取成功」。成功后弹窗可能还留在页面上，额度数字已经变了，不要再点一次。回到「我的题目」，「待处理」里就是新 UUID 和截止时间。领取后 24 小时内要完成提交，所以材料备好再领。可同时在做的题数看页面上「当前窗口可领取题目 N 道」。

「去提交」在自动化浏览器里常打不开，工作台基址在 `sessionStorage` 的 `quiz_answer_url_160`（点过「去提交」才有；没有时沿用已打开过的工作台页面的域名），拼上参数直接打开：

```
<基址>/?talent_id=<专家编号>&uuid=<UUID>&prefill_talent_id=<专家编号>&hide_talent_id=1&prefill_uuid=<UUID>&hide_uuid=1
```

### 查状态和审核意见

```js
async () => {
  const h = { Authorization: 'Bearer ' + localStorage.getItem('magnet_token') };
  const r = await (await fetch('/api/records', { headers: h })).json();
  return (r.records || r.data || r).map(x => x.uuid.slice(0, 8) + ' | ' + x.record_id + ' | ' + x.task_status + ' | ' + x.topic_status);
}
```

`/api/records` 秒回。`/api/record?record_id=` 很慢，常超过 15 秒。审核意见直接读页面：刷新后等 10 到 20 秒遮罩消失，取 `document.body.innerText` 里「审核区」那一段。

### 附件页

后台启动本机服务，页面自己来取：

```bash
python3 magnet/代填脚本.py 02_量化投研与交易_恒指调整
```

页面里依次执行 `upload.js`、`fill.js`、`check.js`：

```js
async () => {
  const s = await (await fetch('http://127.0.0.1:8765/fill.js')).text();
  return await (0, eval)(s);
}
```

- `upload.js` 返回「已交给上传框：N 字节」。等 8 秒，页面出现「已解析 N 个业务文件」。难度筛查退回后返修，同样走这一步，等于点「替换附件包」。8.9MB 的包（解压后 53MB）上传和解析都正常。
- `fill.js` 返回「全部填好：N 个下拉」。出现 `MISS` 是选项文字对不上。
- `check.js` 返回「与 README 一致」。
- `#skipDeid` 不勾。
- 提交：`window.confirm = () => true` 后点 `#btnSubmit`。提交要二三十秒，遮罩 `.progress-mask` 显示进度百分比，等待要拆成几次调用（单次 15 秒会超时）。用 `/api/records` 看状态是否变成「附件校验中」。失败时出现 `.progress-mask.is-error` 弹层。

选择器：`#role #duration #scope #context #purpose #requirements #dlvOverall`，上传框 `#zipInput`，清单行 `.name-select .acc-select .cat-select`，交付物行 `.dlv-row`（`.dlv-name .dlv-type .dlv-ext-select .dlv-req`），加行 `#btnAddDlv`。文本框改 `value` 后要派发 `input` 事件。选完一个下拉整行会重画，每一步重新取行。

### Query 页

执行 `query.js`，返回「已填好：N 字，参考=Q1」。选择器是 `#queryText` 和 `input[name="query-reference"][value="Q1"]`。提交同上。用完结束本机服务。

### 评估页

评估表在同源 iframe 里：`eval.html?record_id=<记录号>&embed=1`，用 `document.querySelector('iframe').contentDocument` 操作。

| 位置 | 选择器 |
| --- | --- |
| 模块 A | `#aList article`，标准描述 `textarea[data-k="standard"]` |
| 模块 B | `#bList article`，描述 `title`，合格条件 `expected`，例外边界 `boundary`（都是 `textarea[data-k=…]`） |
| B 的三家 | 每条里的 `.model-assessment`，按 M1、M2、M3 顺序，证据 `textarea[data-k="evidence"]` |
| 提交、校验、状态 | `#btnSubmit`、`#formErrors`（有 `show` 类表示有错）、`#liveStatus` |

下拉不是原生 `select`，是 `.select` 里的 `.select-option`，文字在 `.opt-main` 的第一个文本节点，直接 `click()` 选项即可。按字段名找下拉：条目里 `.field-label` 含「类型」「影响程度」「是否有中间状态」「关联 A 标准」的 `.field`。

顺序：A 的文字、类型、影响程度；B 的文字、类型、影响程度、关联 A；最后三家判定和证据。B 的影响程度必须和关联的 A 一样。一次调用填 5 到 10 条。

只跑校验不提交：把 iframe 的 `confirm` 换成返回 `false` 再点提交，结果在 `#formErrors`。正式提交换成返回 `true`，要二十多秒，成功后 `#liveStatus` 是「已提交」。草稿在点下拉后约 0.8 秒写入 localStorage。

### 下载三家产物

```js
async () => {
  const h = { Authorization: 'Bearer ' + localStorage.getItem('magnet_token') };
  const r = await (await fetch('/api/artifact?record_id=<记录号>&slot=M1&index=0', { headers: h })).json();
  return btoa(r.url);
}
```

签名地址在页面里取会被跨域拦掉。返回 base64，终端里解码后用 Python 下载到 `/tmp`。每个产物是 `deliverables.zip`。读 xlsx 时同时读单元格显示格式，判格式类缺点以打开表时看到的为准。

### 取平台上锁定的附件

评估和 Solution 对照的必须是平台锁定版，不是仓库里的文件。

```js
async () => {
  const h = { Authorization: 'Bearer ' + localStorage.getItem('magnet_token') };
  const rec = await (await fetch('/api/record?record_id=<记录号>', { headers: h })).json();
  const f = (rec.record || rec).attach_zips[0];
  const res = await fetch('/api/file?record_id=<记录号>&kind=attach_zip&file_token=' + f.file_token, { headers: h });
  const zip = await JSZip.loadAsync(await res.blob());
  return Object.keys(zip.files);
}
```

### 评估表自查

- 写「附件里没有某句话」之前，在锁定版附件里全文搜一遍。
- 每条 A 压成一句「查什么」，有重复就合并。
- 「恰好一家不满足」用一个能改变数字或判断的单家缺点，不靠格式问题。
- 证据只写能定位的事实：文件名、工作表、单元格或段落、原文。
- 判定前把三家同一位置都看一遍。
- 人审改了题包后产物会重新生成，不能沿用旧判定。
