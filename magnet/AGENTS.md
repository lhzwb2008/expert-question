# Magnet 出题：给 agent 的工作说明

这份是 `magnet/` 唯一的总说明，写给在 Cursor 里接手 Magnet 出题的 agent。前半是浏览器代填工作流，后半是项目规则、每道题的状态和经验。每道题要填的原文在该题目录的 `README.md`。

用户的固定要求：

- 全程用中文回复。
- 题目和以前项目的旧案例一对一转换，不合并，不换题。
- 预计任务耗时按传统人工估，填整数分钟。
- 附件按实际工作材料写，不出现「本题」这类出题口吻。
- 每道题只有一个 `README.md`，代码块里只放能直接粘贴的原文，不写解释。「具体任务要求」写成一段，放在一个代码块里。
- 改完题目 `README.md` 后运行 `python3 生成复制页.py`，生成带复制按钮的 `复制页.html`。
- 点工作台上的最终「提交」前要用户点头。用户说「填」只填，说「提交」才提交。
- 工作台链接、token、签名下载地址都不写进仓库。

## 代填工作流

### 0. 打开工作台

用户给的工作台链接形如：

```
https://<网关域名>/?talent_id=<专家编号>&uuid=<题目 UUID>&prefill_talent_id=<专家编号>&hide_talent_id=1&prefill_uuid=<题目 UUID>&hide_uuid=1
```

换题时只换两处 UUID，专家编号不变。UUID 和题目目录的对应见下文「当前领题」。

浏览器用 `cursor-ide-browser`：

1. `browser_tabs` 列出标签页，记下工作台那个 tab 的 `viewId`。
2. `browser_navigate` 传 `url` 和 `viewId`，在原 tab 里换题。
3. `browser_lock` 锁定，全部做完再解锁。
4. 读页面、填表都用 `browser_cdp` 的 `Runtime.evaluate`，并且每次都传 `viewId`。浏览器里常开着本地 `复制页.html`，`file://` 页面不能用 CDP，不传 `viewId` 可能落到那个 tab 上被拒。
5. 每次 `CallDynamicTool` 都带上 `namespace` 和 `toolName`。

打开后有几秒「正在进入工作台」的遮罩。第一次读页面时等 6 秒：`new Promise(r => setTimeout(() => r(document.body.innerText.slice(0, 3000)), 6000))`，`awaitPromise` 设为 `true`。读 `innerText` 比 `browser_snapshot` 快，也能看到状态和校验提示。

### 1. 附件页（2026-11-13 恒指调整已实际跑通）

全部由 `代填脚本.py` 完成，数据从题目 `README.md` 读，不手写长中文串。手写转义容易错一个字，核对也难。

**上传附件包。** 浏览器工具不允许直接给文件框设本地路径，改为在本机临时提供压缩包，让页面自己取：

```bash
cd magnet && python3 代填脚本.py 上传 04_量化投研与交易_恒指调整
```

这条命令要放到后台跑（`block_until_ms: 0`），它会一直在 `127.0.0.1:8765` 提供压缩包，同时写出 `/tmp/magnet_上传.js`。读出这个文件，整段作为 `expression` 执行，`awaitPromise: true`。页面用 `DataTransfer` 把文件放进 `#zipInput`，再触发 `change` 事件，和用户拖进去的效果一样。返回「已交给上传框：N 字节」后，等 8 秒再读页面，应出现「已解析 N 个业务文件」，附件清单自动按包内文件列好行。确认后结束后台进程。

**填其余字段。**

```bash
python3 代填脚本.py 附件页 04_量化投研与交易_恒指调整
python3 代填脚本.py 核对 04_量化投研与交易_恒指调整
```

先执行 `/tmp/magnet_附件页.js`，应返回「全部填好：N 个下拉」，有 `MISS` 就是选项文字对不上。再执行 `/tmp/magnet_核对.js`，应返回「与 README 一致」，否则逐行列出不一致的字段。最后读页面，三条附件门槛（核心文件 ≥ 5、私有文件 ≥ 1、噪音 ≤ 30%）都应是 ✓。

两段 JS 都把整道题的数据嵌在里面，每段约 4000 字符。执行时把文件内容原样贴进 `expression`，一次就行，不用拆。

**提交。** 用户同意后点 `#btnSubmit`，附件页不弹确认框。点完等十几秒再读页面：失败时会出现 `.progress-mask.is-error` 弹层，正文是原因，按「知道了」关掉，表单内容还在。已知的一种失败是「你已提交 3 道题目，均未通过一阶段，暂不可提交新题目」：前面提交的题一道都没过一阶段时，平台不收新题，只能等。

附件页的结构，脚本就是按这些写的：

| 字段 | 选择器 |
| --- | --- |
| 具体岗位 | `#role` |
| 预计任务耗时 | `#duration` |
| 任务范围与口径、业务背景、任务目的、具体任务要求 | `#scope`、`#context`、`#purpose`、`#requirements` |
| 整体要求 | `#dlvOverall` |
| 上传框 | `#zipInput`（隐藏的 `input[type=file]`），按钮是 `#btnPickZip` |
| 附件清单每一行 | 文件名 `.name-select`，公开/私有 `.acc-select`，核心/噪音 `.cat-select`，三列按行对齐 |
| 交付物每一行 | `.dlv-row`，文件名 `.dlv-name`，类型 `.dlv-type`，扩展名 `.dlv-ext-select`，内容 `.dlv-req`。加行用 `#btnAddDlv` |
| 提交 | `#btnSubmit` |

几个坑：

- 文本框要先改 `value`，再派发 `input` 事件，否则表单状态里不会存。
- 交付物类型的选项是：文字文档、PDF、表格、演示文稿、图片、其他。README 标题里写「文档」，对应的是「文字文档」。扩展名下拉要等选完类型才有选项，选项的 `data-value` 不带点，比如 `docx`。
- 选完一个下拉，这一行会整行重画，之前拿到的元素就失效了。每一步都要重新 `querySelectorAll` 取行。
- 领域下拉是链接带进来的，不用动。

### 3. 评估页

评估表的内容要看完三家产物再写，没法从 README 生成。下面是填表的方法。

#### 评估表在 iframe 里

评估表是同源 iframe：`eval.html?record_id=<记录号>&embed=1`。`browser_snapshot` 看不到里面的控件，要用 `browser_cdp` 的 `Runtime.evaluate` 通过 `document.querySelector('iframe').contentDocument` 操作。iframe 的脚本 `contentWindow` 也能拿到。

表单结构：

| 位置 | 选择器 | 说明 |
| --- | --- | --- |
| 模块 A | `#aList article` | 预置 15 条。标准描述是 `textarea[data-k="standard"]` |
| 模块 B | `#bList article` | 预置 8 条。描述 `textarea[data-k="title"]`，合格条件 `textarea[data-k="expected"]`，例外边界 `textarea[data-k="boundary"]` |
| B 的三家判定 | 每条 B 里的 `.model-assessment`，按 M1、M2、M3 顺序 | 判定下拉，加 `textarea[data-k="evidence"]`。选「满足」后证据框隐藏并清空 |
| 补充说明 | `#b2` | 选填 |
| 模块 C | 「是否存在敏感红线内容」默认「无」 | 没有极高敏感内容就不动 |
| 提交 | `#btnSubmit` | 文字是「提交评估表」 |
| 校验结果 | `#formErrors` | `show` 类表示有错，正文是错误清单 |
| 状态 | `#liveStatus` | 提交成功后是「已提交」 |

#### 文本框和下拉怎么填

文本框监听的是 `input` 事件。直接改 `value` 不会存进表单状态，必须再派发一次：

```js
el.value = text;
el.dispatchEvent(new Event('input', { bubbles: true }));
```

下拉不是原生 `select`。每个下拉是 `.select`，里面有 `.select-trigger` 和 `.select-menu .select-option`。选项的文字在 `.opt-main` 的第一个文本节点里，后面跟着灰色说明，所以要取第一个文本节点比较。直接对选项元素 `click()` 就会触发保存，不用先展开菜单。

按字段名找下拉：在条目里找 `.field`，它的 `.field-label` 含字段名，例如「类型」「影响程度」「是否有中间状态」「关联 A 标准」，再取其中的 `.select`。

可选值：

- 类型：结果正确性、专业质量、指令遵循、格式、语气与沟通
- 影响程度：关键、重要、一般
- 是否有中间状态：无、有
- 关联 A 标准：A1 到 A15，以及「无对应 A」
- 模型判定：满足、部分满足、不满足

先在页面里装好几个帮手函数，后面每次调用只传数据，命令会短很多，也不容易把长中文串写坏：

```js
window.__doc = () => document.querySelector('iframe').contentDocument;
window.__setTA = (el, v) => { el.value = v; el.dispatchEvent(new Event('input', { bubbles: true })); };
window.__lab = (o) => { const m = o.querySelector('.opt-main'); return m ? m.childNodes[0].textContent.replace(/\s+/g, ' ').trim() : o.innerText.trim(); };
window.__pick = (sel, label) => { const hit = [...sel.querySelectorAll('.select-option')].find(o => window.__lab(o) === label); if (!hit) return 'MISS ' + label; hit.click(); return 'ok'; };
window.__field = (root, name) => { const f = [...root.querySelectorAll('.field')].find(el => (el.querySelector('.field-label')?.innerText || '').includes(name)); return f && f.querySelector('.select'); };
```

一次调用填 5 到 10 条。一次塞太多，工具会因为参数太长出错。

#### 先填 A，再填 B

顺序：A 的文字，A 的类型和影响程度；B 的文字，B 的类型和影响程度，B 的关联 A，最后三家判定和证据。关联 A 的下拉选项是从 A 的文字生成的，A 没填完就填 B，选项里看不到内容。

两条会挡住提交的规则：

- B 的影响程度必须和它关联的那条 A 一样。不一样时校验报「影响程度与关联 A 的不一致」。先定 A，再让 B 跟着 A。
- 只统计关键和重要的 B：两家及以上「不满足」至少 7 条，三家都「不满足」至少 3 条，恰好一家「不满足」至少 1 条。「部分满足」不计入。

A 的类型配额：结果正确性、专业质量各至少 4 条，指令遵循、格式各至少 2 条，语气与沟通至少 1 条；15 条时单一类型最多 6 条。

#### 不提交，只跑校验

把 iframe 的 `confirm` 换成返回 `false`，再点提交。表单会把全部校验跑一遍，结果写进 `#formErrors`，但不会发出去：

```js
const f = document.querySelector('iframe');
f.contentWindow.confirm = () => false;
f.contentDocument.querySelector('#btnSubmit').click();
f.contentDocument.querySelector('#formErrors').innerText;
```

`#formErrors` 没有 `show` 类、内容为空，就是全部通过。

用户同意提交后，把 `confirm` 换成返回 `true` 再点一次。提交要二十多秒，进度条会停在 90% 左右一阵。成功的标志是 `#statusToast` 显示「评估表已提交」、`#liveStatus` 是「已提交」。之后外层页面还会显示一阵「正在同步评估结果」，那是同步题目状态，不影响提交结果。

表单的草稿存在浏览器的 localStorage 里，只在点下拉后约 0.8 秒写一次。所以最后一步最好是点一个下拉，或者直接提交。

### 4. 下载 M1、M2、M3 的产物

评估页左侧有三个「下载」按钮。它们调用的是：

```
GET /api/artifact?record_id=<记录号>&slot=M1&index=0
Authorization: Bearer <localStorage 里的 magnet_token>
```

返回一个火山引擎 TOS 的签名下载地址。记录号就是 iframe 地址里的 `record_id`。

在页面里用 `fetch` 去取这个签名地址会被跨域拦掉，要拿到地址后在终端用 Python 下载。签名地址很长，从工具输出里手抄进命令容易抄错一两个字符，结果是 `SignatureDoesNotMatch` 403。稳妥做法：在页面里把地址 base64 编码后返回，终端里解码再下载：

```js
// 页面里
const token = localStorage.getItem('magnet_token');
const res = await fetch(`/api/artifact?record_id=${rid}&slot=M3&index=0`, { headers: { Authorization: 'Bearer ' + token } });
btoa((await res.json()).url);
```

```python
# 终端里
import base64, urllib.request
url = base64.b64decode(encoded).decode()
data = urllib.request.urlopen(urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0"})).read()
```

产物放在 `/tmp` 下，不进仓库。下载完删掉含签名地址的临时脚本。

每个产物是 `deliverables.zip`，里面是题目登记的几份 docx 和 xlsx。不用装额外库，Python 的 `zipfile` 加 `xml.etree` 就能读：docx 读 `word/document.xml` 里的 `w:t`；xlsx 先读 `xl/sharedStrings.xml`，再按 `xl/_rels/workbook.xml.rels` 找每个 Sheet。注意 rels 里的路径可能是 `/xl/worksheets/sheet1.xml` 这种绝对路径，去掉开头的 `/` 再读，不要再拼一个 `xl/`。有的模型把日期写成 Excel 序列号（例如 44200），读出来是数字。

#### 读产物时对什么

对照底稿里的标准答案。QQQ 模拟盘的在 `high-econ/一期/qqq_turtle_gate/answer/标准结果.md`，逐笔在同目录 `official_trades.csv`。底稿只能自己用，不能把「标准答案」字样写进评估表。

找 B 的缺点时，按数字逐项对：期末权益、笔数、费用、关键次数、回撤、期末持仓，再看结论和依据。证据写「具体数字 + 文件名 + 位置」。另外核对模型引用的规则原文是否真的在现行附件里：附件改过版本时，模型可能引用到旧版本里才有的句子，这本身就是一条可核对的缺点。

## 项目规则

这份说明给后续出题、改 Query、填评估表和做 Solution 用。规则来自 2026-11-13 收到的两份项目文档，以及当天已经领到的两道题。两份文档有冲突时，以出题规范 v4.1（2026-11-02，更新人邓乃夫）为准。操作手册里的旧截图如果还显示三份合成 Query 或「业内共识」，按 v4.1 做，不按截图做。

工作台地址和登录不在这里记录。打不开时，用电脑上的 Chrome，允许第三方 cookie，清缓存后再进。

### 这个项目在收什么

项目要看主流模型能不能完成白领、知识密集型工作。简单制表、写邮件不收。要的是专家日常会做、模型仍然做不完全的任务，做成一套题包。

一道题最终有六样东西：

1. 任务说明。交代业务为什么发生、要支持什么判断、必须交出什么。系统用它生成 Query 初稿。写得越准，后面返修越少。
2. 附件。完成任务真正要用的前序材料。模型和专家拿到的是同一套输入。
3. Query。给模型的任务命令。v4.1 起系统只给一份初稿，专家在初稿上改，或者自己写。
4. 评估表，以及 M1、M2、M3。同一条 Query 和同一套附件发给三个模型。评估表是专家对三份产物的结构化判断，用来给后续评分标准提供专业输入。
5. 专家 Solution。专家自己按当前 Query 和附件做出的可交付成果，用来和模型产物对比，也用来证明这道题做得出。

好任务同时满足四点：真实、可解、专业、可验收。材料要完整，要求要清楚，难度来自领域判断，不来自故意缺信息或设陷阱。

### 每道题的提交稿怎么放

每道题一个文件夹，里面只有这几样：

- `复制页.html`：由 `README.md` 生成的带复制按钮的页面，填表时用它。
- `README.md`：这道题在工作台上要填的全部内容，按页面顺序排。附件页的每个字段、附件清单的选择、每个交付物、整体要求，再到 Query 页的参考 Query 和 Query 正文，都写在这一个文件里。
- `附件/`：压缩包里的文件原件。
- `某某_附件包.zip`：要上传的压缩包，由 `附件/` 打出来。
- 打包或核对用的脚本（有才放），不上传。

题目 `README.md` 的写法：

- 一个字段一个小标题，标题就是页面上的字段名。内容放在代码块里，代码块里的每一个字都是要粘进页面的，点一下复制就能用。
- 代码块外面不写解释、不写理由、不写注意事项。解释和经验写在这份总说明里。
- 下拉框选的东西没法粘贴，写在标题或表格里：交付物的类型和扩展名写在标题上，例如「交付物 1｜文档｜.docx」；附件清单用表格列出每个文件选公开还是私有、核心还是噪音。
- 交付物的文件名和内容说明各占一个代码块，因为页面上是两个格子。具体任务要求在页面上是一个格子，所有要求写成一段话，放在一个代码块里。
- 题目改版时直接改这个文件，不另存第二份。旧版本靠 git 记录。
- Cursor 的 Markdown 预览里代码块没有复制按钮。改完 `README.md` 后在 `magnet/` 下运行 `python3 生成复制页.py`，每道题文件夹里会生成 `复制页.html`，用浏览器打开，每个字段右上角有「复制」按钮。`复制页.html` 由脚本生成，不手改。在工作台上代填时用同目录的 `代填脚本.py`，它读的也是题目 `README.md`，所以 README 的标题和表格格式不要随意改：字段标题要和页面字段名一致，附件清单保持三列表格，交付物标题保持「交付物 N｜类型｜.扩展名」。

在工作台上从头到尾的顺序：

1. 领题，记下 UUID。
2. 附件页：上传压缩包，逐行选附件清单，填具体岗位、预计任务耗时、任务范围与口径、业务背景、任务目的、具体任务要求、交付物、整体要求，点提交。
3. 等附件机审。不通过就按意见改 `附件/` 里的文件，重新打包，点「替换附件包」，再提交。
4. Query 页：右侧整段换成题目 `README.md` 里的 Query，参考 Query 选「合成 Query Q1」，点提交。
5. 等题目机审和步数。步数不足会退回附件页，这时附件包和任务说明都要按新版本重填。
6. 评估页：三份模型产物出来后填评估表。
7. Solution 页：评估表通过后，上传自己做的交付物压缩包。
8. 等初审、复审。

### 步数门槛：新闻过滤为什么被判「过于简单」

题目机审通过后，系统让模型实际做一遍题，数它执行了多少步。不到 25 步就判为过于简单，退回附件待提交。页面不显示具体步数，也不给原因。下面的原因是对照两道题的材料推出来的：同一天交的两道里，QQQ 模拟盘过了，新闻过滤没过。

#### 根本原因：把「难做对」当成了「做得久」

前两个项目的难度标准是得分：模型最终得分不超过 50 分才算合格。那些题的复杂在于容易算错、容易下错结论。Magnet 的第一道闸看的是执行步数，不看对错。一道题可以很容易做错，同时几步就做完。新闻过滤正是这样：时区、夏令时、改期的发布日都是容易错的地方，但模型不管对错，写一段程序跑完就交卷。

这个风险在 `high-econ/一期/qqq_turtle_gate/README.md` 里早就写过：规则写进手册后，强模型可能一轮写完程序就交卷，步数不一定够。选题时没有按这一条筛，是这次退回的直接责任。

#### 具体原因

1. 整道题只有一条计算链。受限事件表、逐笔台账、方案建议书三份交付物，都是同一段回放程序的输出。交付物数量是三份，实际工作只有一件。
2. 规则写成了可以直接照着编程的说明书。《A03》把三个时区和两国夏令时的切换规则列成了表；《A05》点明了日程里哪些名称的行算受限事件；《A09》把四个方案的改动和比较顺序逐条写死。模型不需要自己判断哪一行算事件、时间怎么换算，照着抄进程序即可。
3. 《A02》把每个文件是什么、用来做什么都列了出来。模型不用自己翻文件、弄清材料之间的关系。
4. 要读的材料少。九个文件里八个是几 KB 的短文，唯一的大文件是行情，只能用程序读，读它只算一步。
5. 没有需要对账的第二套数字。没有另一位同事的结果，没有另一个数据来源，没有新旧版本的规则。做完就是做完，没有东西可核对。
6. Query 的要求和任务说明的四条一一对应，每条都是「按某文件算出某结果」，没有需要取舍或需要先查清再决定的事。

#### QQQ 模拟盘为什么过了

同样是回测，QQQ 这道多出了几件互相独立的工作：按参数手册重算一套；把同事那一版的做法也弄清楚，逐项解释差在哪里；用日线文件和另一份行情导出互相核对价格是不是复权价，再回答这对第三条门槛有没有影响。三份交付物对应的是三件不同的事，不是一段程序的三个输出。

#### 选题和设计时按这几条筛

- 先问「模型要分开做几件事」。只有一条计算链的题不交，哪怕它很容易算错。至少要有三件互相独立、各自要读材料和出结果的工作。
- 交付物之间要有对账关系。两套数字、两个来源或两个版本，要求解释差异，比多交一份汇总表有用得多。
- 判断留给做题的人。规则文件写业务规则本身，不替人把「哪一行算、先算什么、怎么换算」列成步骤。真实的制度文件本来也不会这样写。
- 不要用一份交办把每个附件的用途列成清单。
- 材料的份数和种类要对得上工作量。十几份需要逐份看的文件，比一个 46MB 的行情文件更能体现工作量。
- 不靠凑步数。不加无关文件、不加无意义步骤、不故意缺材料，这些本身就是退回理由。加厚只能来自业务里真实存在的并行事项、对账和例外处理。
- 提交前自己掂量一遍：一个熟练的人能不能写一段程序把所有交付物一次跑出来。能，就不交。
- 转换旧案例时不要替模型做前处理。旧案例为了让答案唯一，常把数据合并、筛选、对齐好再给。Magnet 要的是业务里拿到手的原始形态，核对和整理本身就是工作。
- 题目和旧案例一对一转换，不把几道题并成一道来凑工作量。

#### 不换题，不合并：在这道题本身加厚

题目和以前项目的案例保持一对一，以后每道题都要单独转格式提交。所以不把几道题并成一道，也不换题，只把这道题在业务里本来就有、第一版却被省掉的工作放回来。

第一版其实是把题目做薄了：行情已经替模型把买价、卖价合并好并按交易时段筛过；交办把每个文件的用途列成了清单；交付物只留了同一段程序输出的三份。这道题在以前的项目里通过过，那边的门槛是模型得分和「不少于 50 步或超过 40 分钟」，这边换了运行环境和计步方式，页面又不给步数，所以不能确定差了多少步。还有一种可能没法排除：46MB 的单个行情文件让模型没能正常读完就提前结束。想确认，可以在飞书群里向工作人员要这道题的实际步数。

重做版（2026-11-13）做了这些改动，标答不变：

| 改动 | 第一版 | 重做版 |
| --- | --- | --- |
| 行情 | 一个合并好、筛好时段的 46MB 文件 | 数据组的原始存档：买价、卖价分开，按 UTC 年份各一个文件，共 6 个，最大 19.2MB |

| 交付物 | 3 份，同一条计算链 | 5 份：新增《行情核对记录》和《方案差异清单》 |
| 独立工作 | 回放一件 | 核对行情、确定受限事件、回放、逐日比较方案差异、形成建议 |

新增的两份交付物都是上线复核里本来要做的事：原始行情拿来先核对，四个方案之间差在哪些日期、因为哪些事件要说得清。它们和回放结果互相对账，不是同一段程序顺手多导出的表。

`打包.py` 负责导出分年文件、核对、打包。核对的做法是按《A03》写明的回放范围从 6 个文件重建行情，再和底稿的合并行情逐行比对：598,067 行、476 个伦敦交易日，完全一致。所以底稿的标答和 `rebuild.py` 仍然可用。脚本要用带 pandas 的解释器跑：`/opt/homebrew/bin/python3.13 打包.py`。

按年份和买卖方向分文件是数据源的原始形态，同时让每个文件不超过 20MB。这不等于可以把文件随意拆碎凑数：不按月、按周再拆。

这一版仍然不能保证过 25 步，本地没法跑平台的模型。再被退回，这道题的机审返修就用到第 3 次。那时先向工作人员要步数，再决定是否继续。

2. 附件机审中。查相似度、质量、多样性。超过 1 小时仍无意见或显示运行异常，到群里找工作人员。
3. 题目待提交。系统给一份 Query 初稿。改完再提交。附件从这里开始锁定。
4. 题目机审中。查 Query 相似度，以及 Query 和附件能否闭环。通过后系统跑任务步数。
5. 步数达到 25 步才生成 M1、M2、M3。少于 25 步视为太简单，退回附件待提交，整题重做。
6. 专家评估中。读三份产物，填评估表并提交。
7. 评估表机审中。不通过则回到专家评估中，只能改评估表。
8. Solution 待提交。按锁定的 Query 和附件做专家成果，右侧上传压缩包。
9. Solution 机审中。不通过只改 Solution。
10. 初审、复审。都通过后是一阶段通过，等待结算。不可修复则一阶段拒绝，题目废弃。

评估环节不能退回附件或 Query。任务说明和 Query 必须在提交前就站得住。评估时才发现题目太简单、附件缺件或 Query 泄题，不能整题重做，只能在评估表里处理内容问题。机审卡住、系统没跑完，联系工作人员重试，不要当成内容返修。

返修上限：机审最多 5 次，人审最多 3 次。超过后官方废弃，不再返修。只差小改就能过、但次数已经用完时，填飞书表单，选「返修次数已达到上限」，把理由写进具体问题描述：https://meetchances.feishu.cn/share/base/form/shrcnhKVqznMQpazaalXTxVlXGh

初审退回的去向：Query 或 Query 与附件闭环的问题退回题目待提交，并重新生成后面的产物；评估表问题退回专家评估中；附件一眼假或其他不可返修问题直接一阶段拒绝。复审只看初审指出的问题有没有修好。

预计任务耗时低于 480 分钟，直接一阶段拒绝。耗时明显虚高、又无法用任务说明、附件规模、步骤和交付物解释的，也不能过。

申诉：附件机审、题目机审、评估表机审、初审、复审、一阶段拒绝，在有充分理由不接受当前意见时可以申诉，必须写理由，可以附材料。新题的评估表机审异议另外走「专家反馈」，见下文评估表一节。申诉不自动改结果。

### 任务说明怎么填

页面字段和填写要求：

| 字段 | 要求 |
| --- | --- |
| 具体岗位 | 写真实岗位，例如量化风控分析师、量化研究员 |
| 附件包 | 一道题一个 zip |
| 预计任务耗时（分钟） | 只填数字，可以有小数。不少于 480 |
| 任务范围与口径 | 选填。只写不写就会改变结论的时间、对象、边界、口径 |
| 业务背景 | 不少于 60 字。为什么现在做，结果给谁、在什么场合用 |
| 任务目的 | 不少于 30 字。解决什么问题，支持什么判断 |
| 具体任务要求 | 1 到 5 条，每条 20 到 50 字，每条只写一件事。页面若没有这一格，以页面为准 |
| 附件分类 | 每个文件标公开/私有、核心/噪音。页面列名是「核心/噪音」，文档旧称是「非噪音/噪音」，选「核心文件」即可 |
| 交付物 | 文件名不含扩展名，类型和扩展名用下拉框。内容写这文件必须含什么 |
| 整体要求 | 选填。跨文件一致的要求写这里 |

预计任务耗时按传统人工估，不按写一段程序跑完的时间估。计入：理解口径、读材料、做表、计算、专业判断、制作全部交付物、核对、必要的专业沟通、复核修改。不计入：排队、等待审批、与本题无关的会议。可以跨很多天累计，填的是有效分钟数，不是自然日。先拆环节再相加。20 只股票的调仓复核如果手工做表、逐笔核对和写意见，也是数天的工作，不能估成几百分钟。两道已领题目的分钟数和拆法见上面各题，改数字时要连拆法一起改，保证和附件规模对得上。

这一格的单位是分钟，直接填一个整数，例如 `8000`，不要填 `10080`、`8160` 这种按天数乘出来的零头。预计耗时和步数门槛是两回事：耗时填得再大，模型几步做完照样退回。

具体任务要求写结果，不写操作顺序。可以写「按口径生成订单并完成限额检查」。不要写「先清洗，再透视，最后排序」。

任务说明保持中立：

- 不写从附件推导出的答案、异常对象、缺失项、名单、金额、行号和预期结论。
- 不写评分点、模型弱点、本题要考的规则组合、固定解题顺序。
- 附件里已有规则时，只要求依据材料核验，不把决定性条款抄出来再和本题对象绑死。
- 可以允许模型在证据不足时标待核、列待补、缩小范围或给出负向结果。不能把本题实际缺口写成已经发生的事实。
- 不在任务说明里点名哪个文件是噪音。
- 不堆「不得虚构」「仅使用附件」这类套话。

交付物文件名必须带扩展名，扩展名和以后真正要交的 Solution 一致。不要为了通过校验多造一份交付物。

### 附件规则

一道题只传一个 zip。上传后系统解开并列出文件，再逐个选公开/私有和核心/噪音。再次上传会替换整个包。

压缩包要求：

- 默认平铺。页面允许带文件夹，包内不能再套压缩包，也不能有音视频。更稳妥的做法仍是平铺，本仓库两个包都是平铺。
- 核心附件至少 5 个，而且都被任务真正用到。不要把一个文件拆成多份凑数。
- 文件类型至少两类。类型按类别算，xlsx、xls、csv 都是表格，只算一类。当前两道都是表格加文档，已经满足。
- 纯表格、纯文档、纯代码、纯专业格式可以例外，但要同时满足：这是该业务的自然形态；至少 5 个核心文件之间有对象、期间、版本或上下游关系；Query 要求的是专业处理；任务说明写明为什么可以单一类型。能自然附上制度或参数表时，不要用例外把它们省掉。
- 删掉附件后，不能只靠 Query 就做出大部分核心产物。
- 至少有一个附件标私有。
- 噪音用来模拟真实目录，不用于恶意误导。有噪音时建议不超过附件总数的 30%。当前两道没有噪音，全部标核心文件。
- 公开指经官方公开的材料，私有指未经官方公开的材料。行情和官方日程标公开，内部口径、策略、费用、门槛、同事摘要标私有。
- 文件名按业务命名。不要把「核心」「噪音」「公开」「私有」写进文件名，这两项只在分类里选。
- 单文件建议不超过 20MB，全部附件建议不超过 300MB。新闻过滤的分钟线超过 20MB，见该题说明。
- PDF 要能抽出文字。关键数字不要只放在图片里。不要交加密文件或必须用专用软件才能打开的格式。

内容卫生：

- 附件按实际工作材料来写。行情、日程、策略、账户规则、同事备忘和签发标准，都是业务里会留下的文件，不是为评测现编的试卷。2026-11-13 新闻过滤被退回，原因就是《A05》写明自己是「参照多家平台条款形成的本题专用口径」。这类句子不能再出现。
- 规则、门槛和方案文件要能看出制定部门、生效时间和适用范围。正文不要写「本题」「本题口径」「出题」「评分点」「标准答案」「考点」，也不要写「参照多家条款改编，不等同于官方原文」。
- 交办写成同事之间的备忘，不要写成给模型的提示词。不要出现「你是……」「不得下载」「仅使用所附」「不要把某个结果写成正式答案」。
- 只删掉暴露句、规则正文原样再交，不符合这次机审意见。文件要改成业务里实际使用的文本。受限窗口、违规处理和账户终止这些判断规则可以保留，因为它们就是账户正在执行的规则。
- 附件里不能有最终名单、完整解题步骤或出题人指令，也不能标哪个文件是噪音。同事的不同做法可以留在他自己的备忘里，不要在另一份文件里点破哪一版赚钱、哪一版不该签发。
- 若附件机审认定材料是合成或测试材料，退回后改的是文件本身。初审若认定一眼假，会直接一阶段拒绝，不再给改附件的机会。
- 平台现在负责脱敏，专家可以不再先脱敏。若自己先脱敏，用不可回推的占位符，例如 `[员工_001]`。只改文件名或轻度打码不算脱敏。脱敏后业务主键和勾稽必须还在。
- 不要放密钥、账号、真实登录链接、`.env`。模型没有这些登录，题会因缺材料作废。

### 工作台上已经碰到的操作

一道题只上传一个压缩包。上传后系统解开文件，要逐行选公开/私有和核心/噪音。两道题的文件全部是核心文件。行情和官方日程选公开，内部规则、策略、费用、同事备忘和交办选私有。

任务说明里的「交付物」只登记文件名、类型和内容。建议书、测算表和台账要等评估表通过、进入「Solution 待提交」后再上传。

附件机审不通过时，按意见改文件，重新打成一个压缩包替换上传。新闻过滤第一次被退，是因为规则文件写成了评测口径，不是因为缺了某一列。改完规则的来源、生效时间和交办口吻后，第二次通过。

进入 Query 页后：

- 左侧审核区先是空的，显示「题包审核后开放」。这是正常的，提交 Query 之后才会有审核意见，飞书也会提醒。
- 右侧三段占位是「背景」「范围」「要求」。整段替换，不要留着占位说明。
- 页面下方「参考 Query」选「合成 Query Q1」。系统目前只给一份初稿，最终文字是在这份初稿上补过角色、交付物和待核处理的。选「无」表示完全没有参考初稿。
- 附件已经锁定，这一步不要再上传压缩包。
- 提交后等题目机审。通过后系统跑步数，达到 25 步才生成 M1、M2、M3，然后才填评估表。少于 25 步会退回附件，整题重做。

### Query 怎么改

附件锁定后才能改 Query。发现核心附件真的缺了，不要在 Query 里编造补齐。

v4.1 只提供一份初稿。初稿是待核草稿，不是事实来源。可以基于初稿改，也可以自己写。先用一句话还原「材料、对象、专业任务、交付物」，再按五步改：核事实、核专业任务、核范围、核边界与验收、最后润色。初稿多出来的对象、期间、指标和交付物，如果会改变必答范围，删掉，不要改成「可选」敷衍。

一份 Query 通常要写清七件事：谁在什么场景下接任务、结果给谁用；要判断或计算什么；对象、范围、时间和版本；依据哪些材料做哪些核心工作，但不点名噪音；题内必须遵守的规则、阈值、来源优先级、单位、粒度和主键；证据不足时允许哪些输出状态；交付物的文件名、格式、必含内容和用途。

答案中立：

- 可以写角色、范围、材料关系、判断维度和交付要求。
- 不可以提前写出本题的异常对象、缺失项、名单、数值、正负结论，也不可以要求模型复述专家答案。
- 不可以规定「先看某条、再按固定顺序、超过某数就必须判成某种结论」。
- 材料不足时写「保留已确认事实，标待核，说明对结论的影响」。不要写「由于本例不满足，因此不得……」。

专业难度来自跨材料核对、规则适用、例外处理、多步骤且能复算的计算、交付物之间的口径一致。步数少于 25 会整题退回。强模型如果一轮脚本就交卷，步数可能不够，设计任务时要让专业判断和例外处理真实存在，而不是只交一个汇总数。

提交前按七项自检：事实能否回到附件；有没有无依据扩大范围；有没有泄题用语；删掉附件事实后 Query 是否仍能看出答案方向；有没有把考点和路径写成模板；异常处理是不是条件式；润色有没有改掉约束或造成前后矛盾。

已领两道在改 Query 时特别不要写进题面的话：新闻过滤不要点名最终采用哪一个方案；模拟盘准入不要点名签发还是搁置，也不要复述另一份摘要里的权益和建议。来源冲突时，新闻过滤按平台规则和方案文件，模拟盘准入按参数手册。这些优先级附件里已经有，Query 只要求依附件核验。

### 评估表

等 M1、M2、M3 生成后再填。顺序是：回看 Query 和附件，先写模块 A，再读完全部产物，用真实缺点反推模块 B，最后写模块 C。

三块不能互相代替。A 不评价某个模型。B 的评估项描述也不写模型名，三家表现写在模型证据里。普通质量问题再严重也不放进 C。

#### 模块 A

一份优秀产物应达到的通用标准，任何一份产物都能用同一条来评。

- 至少 15 条，不设上限。写到核心任务和交付物已经覆盖完整就停，不为凑数改写同一句话。
- 结果正确性至少 4 条，专业质量至少 4 条，指令遵循至少 2 条，格式至少 2 条，语气与沟通至少 1 条。
- 任一类型不超过 A 实际总条数的 40%，向下取整。15 条时单类最多 6 条。
- 类型看「修好它主要要改什么」，不看问题严重不严重，也不看这句话是不是出现在 Query 里。
- 每条写清依据、检查对象、合格条件和必要边界。不要只写「专业、全面、准确」。
- 依据只来自三类：Query 的明确要求，附件里的字段、条款或能稳定推出的要求，有明确边界的专业默认规则。新题没有「业内共识」勾选。个人偏好不能写成硬性标准。
- 有中间状态时才分 2 到 4 档。档位要可观察、不重叠、无空档、逐级递进。能直接判断对错的不要硬分档。
- 影响程度按不满足时的业务后果：关键会改变核心结论、主要名单、重要金额或使必需交付物无法使用；重要是还能用但要明显返工；一般是局部优化。不要把所有条都标成关键。

#### 模块 B

记录三个模型真实存在、能定位的缺点，再反推成通用评估项。

- 合计至少 8 条。每个模型至少 3 条真实缺点。
- 只在影响程度为关键或重要的条目里统计：至少 7 条有两家及以上不满足；其中至少 3 条三家都不满足；至少 1 条恰好只有一家不满足。三家都不满足计入「至少两家不满足」。一般条目另计，不计入这组门槛。
- 三家情况只填「满足」或「不满足」。不再使用「部分满足」。
- 评估项描述写评价对象、核查范围、什么事实出现就判不满足、业务影响。模型名称、错误数值和页码写在模型证据里。
- 证据格式是「具体表现 + 文件名 + 位置」。不满足必须指出实际缺点。满足也要写清核查了什么范围。
- 「合格时应满足」写成可以逐项对照的对象、字段、数值、状态或清单，并注明来源。不要用「全部正确」代替。
- 不为了凑 7/3/1 去编造、把同一失败换个说法再计一次，或把一个缺点拆成多个字段。
- 模型用了另一种能复核、前后一致、符合 Query 的做法，不记缺点。材料没有的事实，模型已经标了待确认，也不记缺点。

#### 模块 C

只收极高敏感内容：伦理问题、隐私泄露、政治错误、色情或暴力、其他极高敏感。算错、漏做、专业性不足、虚构一般业务内容，都留在 A 和 B。选「有」时要指定涉及的模型，摘录原文和位置，并说明为什么构成该类型。规则建议最多 3 条，选填，不代表产物已经命中。

#### 评估表被打回

新题：状态是「专家评估中」时，先看具体意见。意见成立就改对应条目。有异议就在右侧「专家反馈」里对那一条勾选「提出异议」，写下异议理由和佐证，写清 Query、附件或产物里的文件名和位置。提交后，这一条跳过机审，进入人工审核。异议不等于通过。确认有问题的条目仍然要改。

旧操作「业内共识」加白只适用于本次优化之前的旧题。这两道是新题，不要找这个勾选。

### Solution

评估表机审通过后才做。它是可以交给同事或决策者使用的正式成果，不是评估表，不是对 M1、M2、M3 的点评，不是解题步骤，也不是把附件抄一遍。

按当时已经锁定的 Query 和附件做完全部交付物。关键数字能回到附件并复算。事实、判断和待核假设分开。文件之间的对象、期间、单位、数字和结论一致。成品里不能出现模型编号、评估表、评分、机审意见或「标准答案」字样。

不能为了迁就 Solution 的写法去改 Query 或评估标准。Solution 机审不通过时只换 Solution 压缩包。

两道题的成品名称以各自任务说明里登记的交付物为准。底稿答案在 `high-econ/` 对应题目的 `answer/`，重算脚本是同目录的 `rebuild.py`。这些文件只供自己复核，不上传。
